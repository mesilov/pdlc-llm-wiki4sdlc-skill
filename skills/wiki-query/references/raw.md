# Категории и единицы raw

`raw/` обозначает разрешённый `raw_root` из [профиля](profile.md).
Дефолтные категории — `sources` и `research`.

| Категория | Содержание | Назначение |
| --- | --- | --- |
| `sources` | Документы, снимки источников, интервью, скриншоты, наблюдения, логи, измерения и результаты проверок | Сохранить исходное свидетельство, его происхождение и контекст |
| `research` | Вопрос, методика, сравнение, расчёты и отчёт отдельного исследования со ссылками на основания | Сохранить ход исследования и воспроизводимость выводов |

Наблюдения и проверки относятся к `sources`. В описании различайте заявление
источника, прямое наблюдение и результат проверки. Название папки не подтверждает
достоверность материала, принятие решения, реализацию или runtime.
Канонический синтез принадлежит `knowledge/domains/` с учётом профиля.
Отдельный исследовательский отчёт нужен, когда методика и сравнение имеют историческую ценность.

## Выбор категорий

Явный `raw_categories` полностью заменяет defaults, включая `[]`.
Категория — имя каталога одного уровня, без разделителей пути, NUL и значений `.` или `..`.
Например, используйте `interviews` и тему `customer`, а не категорию `customer/interviews`.
Опишите назначение пользовательских категорий в схеме проекта.
Пустой список отключает дефолтную карту; размещение определяет схема проекта.
Если поле отсутствует, специальная карта существующей schema имеет приоритет
для агента; иначе используйте две дефолтные категории.
CLI разрешает список профиля или defaults, но не читает смысл schema.
Существующие категории и материалы не перемещаются автоматически.

## Дерево внутри категории

Для новых единиц дефолтная схема:

```text
raw/<category>/<topic>/YYYY-MM-DD-<slug>/
  README.md
  <original files or research artifacts>
```

- `<topic>` — предмет исследования или материала; название в lowercase-kebab-case.
- Дата — день получения материала или начала исследования в часовом поясе проекта.
  Это не дата публикации источника и не подтверждение его свежести.
- `<slug>` — краткое название источника, наблюдения, проверки или исследования.
- `README.md` — обязательная точка входа в единицу, даже если исходный файл один.
- Дополнительные подпапки появляются только при наличии файлов.
  Например, `screenshots/`, `logs/`, `data/` или `scripts/`; фиксированного списка нет.

Исходный текст, JSON, HTML, PDF, изображения и логи сохраняйте в исходном формате.
Не добавляйте метаданные внутрь оригинала и не переписывайте его ради нового дерева.
Сначала сравните URL, происхождение, версию, содержание и контекст с существующими материалами.
Для совпадающего материала используйте прежнюю единицу и её адрес.
Новый снимок источника оформляйте отдельной единицей, не заменяя старый.
При совпадении даты и slug добавьте понятный суффикс версии или контекста.
Исследование может накапливать материалы; изменённые основания и результаты сохраняйте с датами.
Самостоятельный повтор исследования оформляйте новой единицей со ссылкой на предыдущее.

## Корневой README.md по форме OKF

Для новых единиц используйте UTF-8 Markdown с YAML frontmatter по форме концепта
Open Knowledge Format (OKF) v0.2. Поля и границы проверок описаны в [metadata.md](metadata.md).
Типы, обязательность title/description/sources, имя README.md и дерево выше —
локальные соглашения набора. OKF требует только `type` и не задаёт нашу таксономию.
Это не требование преобразовать весь корпус или исходные вложения в OKF.

Минимальные поля корневого файла:

| Поле | Требование набора |
| --- | --- |
| `type` | Непустая строка: `Source material` или `Research study`; пользовательские категории описывают свои типы в schema |
| `title` | Непустое название единицы |
| `description` | Непустое краткое описание с существенными условиями |
| `sources` | Список оснований с уникальными стабильными `id` и непустым `resource` для каждого элемента |

`sources: []` допустим при отсутствии доступного основания, с явным пояснением в тексте.
Например, материал получен напрямую, но у него нет исходного URL или отдельного файла-основания.
Не выдумывайте источник и не считайте такую запись подтверждённой.
Для исследования укажите использованные источники, включая доступные единицы `sources`.
Локальный `resource` разрешается относительно README.md; исходный URL сохраняйте отдельно от снимка.
В локальном raw-контракте используйте относительные адреса внутри checkout.
OKF допускает адреса от корня bundle и недоступные цели; эти правила не равны локальному требованию raw.
Для значимых утверждений добавляйте обычные Markdown-ссылки в тексте:
raw-lint проверяет локальные адреса источников в корневом YAML, а общий CLI
не поддерживает OKF-сноски полностью и не разбирает YAML других страниц.

Учебный пример заголовка; замените примерные значения фактическими:

```yaml
---
type: Source material
title: Пример документации API
description: Снимок документации для сравнения заявленного и наблюдаемого поведения.
sources:
  - id: upstream-documentation
    resource: https://example.org/reference
---
```

В теле README.md обязательно опишите:

1. Происхождение и дату получения; известные автора, дату публикации и версию.
   Неизвестные сведения отметьте явно. Для наблюдения или проверки укажите метод.
2. Контекст: предмет, среду, регион, тариф, параметры или другие существенные условия.
3. Состав: относительные ссылки на фактические файлы и пояснение их назначения.
4. Ограничения: недоступные части, противоречия, неподтверждённые выводы и область проверки.
5. Для исследования — вопрос, методику, выводы с основаниями и оставшиеся неизвестные.

Для timestamp-полей используйте ISO 8601 datetime с явным UTC offset.
`generated`, `verified`, `status`, `stale_after` добавляйте только по [правилам метаданных](metadata.md).
Содержательная правка и успешный lint сами по себе не создают событие `verified`.
Существующие оригиналы и старые единицы не переписываются массово.
Явная схема проекта может заменить этот формат; сохраните provenance и границы подтверждения.

## Проверка агентом

При создании или содержательном обновлении новой единицы проверьте дерево,
frontmatter, источники, даты, адреса файлов и границы утверждений по правилам выше.
При query/audit/lint без записи сообщайте пробелы без автоматической миграции.
`bin/wiki/raw-lint` проверяет форму OKF и локальный контракт корневых README.md:
дерево, наличие файла, настоящий YAML, обязательные поля, ID оснований,
структуры присутствующих метаданных, ISO 8601 timestamp с UTC offset и локальные источники.
Оригинальные вложения и корневые описания категорий не являются единицами проверки.

Выполняйте из целевого checkout:

```bash
python3 -m pip install -r bin/wiki/requirements.txt
bin/wiki/raw-lint --json
bin/wiki/raw-lint raw/sources/<topic>/YYYY-MM-DD-<slug> --json
```

Первую команду выполняйте явно в окружении проекта; raw-lint сам не устанавливает зависимости.
PyYAML 6.0.3 нужен только этой команде; остальные wiki-команды используют стандартную библиотеку.
При изменении единицы передавайте её фактический путь; пути разрешаются относительно cwd.
Без paths проверяются категории профиля. `raw_categories: []` отключает автоматический выбор,
но явные пути внутри raw_root остаются доступны.
Неохваченные legacy-материалы обозначаются предупреждением, а не преобразуются.

`--okf-only` проверяет форму концепта OKF: YAML mapping и непустой строковый type.
Неизвестные типы и дополнительные поля допустимы; optional families не требуются.
Нарушения рекомендаций для присутствующих метаданных выводятся как warnings.
Дерево, дополнительные обязательные поля raw, типы категорий и существование локальных источников
в этом режиме не проверяются. Используйте его для явной схемы, заменяющей локальный контракт,
и дополните собственными проверками проекта.

Коды: `E_OKF_*` — нарушения формы концепта; `E_RAW_*` — локального raw-контракта;
`W_OKF_*` и `W_RAW_*` — замечания к producer guidance или неохваченному scope.
Exit codes: 0 — нет errors, warnings допустимы; 1 — нарушения; 2 — ошибка вызова, профиля или зависимости.
JSON сохраняет режим, категорию scope, checked files, findings, summary и ограничения.
Проверка только читает файлы, не обращается к внешним URL и не исполняет источники.
Она не использует текущее время и не ставит verified.

Этот root lint не подтверждает соответствие всего bundle, reserved index/log,
Markdown payloads, полноту provenance, истинность, свежесть, runtime или аттестацию вычислений.
Ненулевой результат и неохваченные материалы сообщайте отдельно; успешный CLI не заменяет смысловую проверку.
