# Общий контракт wiki-набора

Прочитай этот контракт перед любой процедурой `wiki-*`. Набор состоит из восьми
skills и `bin/wiki/`; переносится вместе с этим общим ресурсом.

## Контекст проекта и пути

Набор работает в целевом проекте, а не в checkout, из которого установлен.
Пользователь и текущий `AGENTS.md` определяют scope, рабочий checkout, язык,
проверки, worktree/branch и поставку. Профиль — `wiki.config.json` в корне
целевого проекта. Имя, context и language берутся из профиля, если не заданы
текущими инструкциями. Источники сохраняют исходный язык, идентификаторы —
написание. Не переносить память, правила веток или публикации исходного проекта.

Перед работой прочитай профиль и [соглашения профиля](profile.md). При неверном
профиле не подменяй его дефолтами. `bin/wiki/status` проверяет механические
предусловия; успешный запуск не доказывает semantic completeness.
Корень CLI определяется от cwd по ближайшей границе Git/config; вложенный
checkout не использует корпус родительского проекта. Команды `bin/wiki/*`
запускай из целевого checkout. Все восемь skills, общий ресурс и CLI составляют
единый комплект; одиночный SKILL.md без соседей не является полной установкой.

**Пути в текстах skills — логические обозначения, не буквальные пути.**
`raw/` означает разрешённый raw_root, `knowledge/` — knowledge_root.
`knowledge/SCHEMA.md`, `index.md`, `synthesis.md`, `GLOSSARY.md`,
`ASSUMPTIONS.md`, `OPEN-QUESTIONS.md`, `log.md` заменяются значениями documents.
`domains/`, `decisions/`, `inbox/`, `archive/` заменяются значениями layers.
Разрешай пути до чтения/записи; в ссылках используй реальные относительные пути.
При `documents.<name>: null` документ отключён: пропусти соответствующий шаг,
сохрани важное знание в действующих слоях. Schema и index нельзя отключать.
Не создавай отключённые документы или пустые каталоги для прохождения workflow.

Без профиля используются raw/knowledge в корне, стандартные имена документов
и слоёв. `corpus_root` переносит оба слоя вместе; независимые raw_root и
knowledge_root имеют приоритет. Пути остаются внутри целевого проекта после
разрешения symlinks. Имя решения и статусы задаёт профиль/схема, дефолты —
`YYYY-MM-lowercase-kebab-case.md` и proposed/accepted/rejected/superseded.
Значение нестандартных статусов прочитай в schema; не переименовывай старые
решения автоматически и не принимай решение только из-за создания record.

Полностью прочитай разрешённые schema и index; затем относящиеся к вопросу
domains, views, decisions, assumptions, questions и evidence. Если обязательная
схема отсутствует, сообщи конкретный недостающий документ; инициализация новой
wiki — отдельный разрешённый scope. Не ограничивай substantive review индексом.

## Общие границы

Перед составлением ответа или изменением авторского текста прочитай
[правила технического письма](writing.md) и все обязательные материалы по его ссылкам.
Применяй полный исходный каталог УТР и чек-лист
в границах задачи; сохранение смысла и свидетельств имеет приоритет перед стилем.

Сохраняй provenance, датированные snapshots, противоречия и уникальное знание.
Факт, hypothesis, decision, specification, implementation и runtime observation
не взаимозаменяемы. Search по index и тексту предшествует созданию новой
canonical page. При работе с терминами прочитай [общие правила глоссария](glossary.md):
формат, канонические названия, синонимы, неоднозначность и границу определения
и применения. Процедура сверки и исправления находится в `wiki-lint`.

Query и report-only audit/lint не записывают файлы или log. Mutation workflow
завершается wiki-lint fix в разрешённом scope; CLI --fix только сортирует
существующие H2-блоки и не заменяет semantic review. Не устраняй unrelated
findings массовыми правками: сообщи оставшиеся замечания с причинами.
Успешный lint подтверждает проверенный scope, а не истинность всей wiki.
Commit, push, PR/MR, merge, CI и deployment определяют запрос и харнес целевого
проекта; завершение wiki workflow само по себе их не разрешает.

## Представления PDLC

Используй карту представлений из schema и index проекта. Если специальной карты
нет, применяй следующие дефолтные вопросы по жизненному циклу продукта:

| Представление | Вопрос и содержание |
| --- | --- |
| `product` | Зачем продукт: ценность, цели, границы, приоритеты, экономика |
| `discovery` | Для кого и какая проблема: пользователи, исследования, гипотезы |
| `experience` | Какую пользу получает пользователь: сценарии, UX, проверка решения |
| `engineering` | Как реализовать: архитектура, ограничения, качество, связи с OpenSpec |
| `go-to-market` | Как вывести на рынок: позиционирование, каналы, pricing, launch |
| `operations` | Как поддерживать: эксплуатация, support, риски, вывод из использования |
| `measurement` | Что получилось: метрики, эксперименты, обратная связь, пересмотр |

Это вопросы к производным страницам, а не обязательные каталоги или этапы
водопада. Представления могут пересекаться; каноническое знание принадлежит
domains. Создавай страницу только при наличии самостоятельного содержания.
Обновляй реально затронутые существующие views; не переноси структуру проекта
под дефолт и не копируй facts/decisions/specs в каждый view.

## Подключаемая трассировка спецификации

OpenSpec отключён по умолчанию (`openspec_root: null` или поле отсутствует).
Не требуй каталог или CLI и не создавай их для query/ingest/research/update/
audit/lint/merge/decide. Если в профиле указан путь, каталог должен существовать;
ошибка подключения сообщается до любых записей. CLI openspec нужен для
проверки изменённых specs, а не для чтения wiki. Не устанавливай его автоматически.

Без OpenSpec сохраняй цепочку `evidence → canonical knowledge → decision`
и связывай доступную спецификацию проекта и implementation evidence. Если их
нет, явно сообщи отсутствие формализации/проверки; proposed остаётся допустимым.

При подключённом OpenSpec сохраняй цепочку `evidence → canonical knowledge →
decision → OpenSpec change/requirement → implementation verification`.
Последние звенья проверяй
только при наличии evidence; намерение и спецификация не доказывают реализацию.

При подключённом OpenSpec и создании/правке продуктового решения добавь раздел
`## Трассировка OpenSpec` и для каждого самостоятельного следствия запиши:

- `linked` — относительные Markdown links к change/spec, точный `change-id`,
  `capability` и имя `Requirement`; в proposal/design/spec должна быть обратная
  ссылка на decision. Если requirement пока не сформулирован, используй deferred.
- `deferred` — формализация ещё не сделана: причина, owner, условие перехода
  к spec и открытый вопрос. Это видимый разрыв; до реализации требуется linked.
- `not-applicable` — выбор не меняет поведение системы, с явным обоснованием.

Статус трассировки не заменяет статус решения. При нескольких requirements
указывай каждый; связь только с каталогом OpenSpec недостаточна. При переносе
change в archive или замене решения согласуй прямые и обратные ссылки.
Query/audit сообщают missing links, отсутствие обратной связи, coverage gaps и
расхождения scope; общий link lint проверяет существование целей, не смысл
Requirement и не весь граф автоматически.

Чистое ingest/research/update знаний не создаёт change автоматически.
При затронутом продуктовом решении проверь его трассировку. Если OpenSpec
подключён, формализацию нового поведения выполняй через него в разрешённом scope. Исторические решения
не переписывай массово ради нового шаблона: gaps сообщаются, исправления —
в scope текущей задачи.
