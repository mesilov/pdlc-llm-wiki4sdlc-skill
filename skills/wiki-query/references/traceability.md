# Трассировка wiki ↔ OpenSpec

Используйте этот контракт, если OpenSpec явно подключён через `openspec_root`
и задача касается спецификации или её оснований. Подключение не разрешает
принимать решения и менять спецификацию вне запроса. Без OpenSpec сохраняйте
цепочку «источник → каноническое знание → решение».

## Цепочка и границы

Исследование проходит через нужные линзы. Результаты и требования хранятся
в `domains/`, свидетельства — в `raw/`, выбранный scope — в решении.
Линзы дают обзоры и ссылки; не копируйте в них требования.

Для выбранного scope сохраняйте связи:

```text
Источник → wiki Requirement → wiki Scenario → решение
                   ↕                 ↕
          OpenSpec Requirement → OpenSpec Scenario
                                        ↓
                            тест → реализация → наблюдение
```

Карта ниже проверяет только wiki, решения и спецификацию. Тесты, реализацию
и наблюдения связывайте отдельно, по доступным свидетельствам.
`openspec validate` и `bin/wiki/lint` не доказывают смысловое соответствие.

## Стабильные ID

Добавьте ID в заголовки канонической wiki-страницы и файлов спецификации:

```markdown
### Requirement: [WK-INV-R01] Приглашение в команду
Пользователь с нужными правами может пригласить участника.

#### Scenario: [WK-INV-S01] Новый пользователь принимает приглашение
Given действующее приглашение
When адресат создаёт аккаунт и принимает приглашение
Then аккаунт получает согласованную роль в команде
```

В OpenSpec используйте тот же формат с отдельными ID, например `OS-INV-R01`
и `OS-INV-S01`. Сохраните обычные правила OpenSpec для требований и сценариев.
Это соглашение набора, а не встроенная функция OpenSpec.

ID начинается с ASCII-буквы и содержит буквы, цифры, `.`, `_`, `-`.
Название можно уточнять, ID сохраняйте. В одной карте ID уникальны во всех
wiki-файлах и файлах OpenSpec. Примеры в блоках кода CLI не учитывает.
Каждый Requirement имеет хотя бы один Scenario. Сценарий находится под своим
Requirement: H3 для требования, H4 для сценария.

## Карта

Создайте `domains/<feature>/traceability.json` в настроенном корне знаний.
Название файла фиксировано; `domains` разрешается через `layers.domains`.
Используйте один уникальный `feature` на карту:

```json
{
  "version": 1,
  "feature": "invites",
  "wiki_files": ["domains/invites/requirements.md"],
  "specs": [
    {
      "capability": "invites",
      "path": "changes/add-invites/specs/invites/spec.md"
    }
  ],
  "decisions": ["decisions/2026-10-invites-scope.md"],
  "links": [
    {
      "requirement": "OS-INV-R01",
      "scenario": "OS-INV-S01",
      "wiki_requirements": ["WK-INV-R01"],
      "wiki_scenarios": ["WK-INV-S01"]
    }
  ],
  "exclusions": [],
  "review": {"status": "pending"}
}
```

`wiki_files` и `decisions` содержат пути от корня знаний.
Wiki-файлы находятся в настроенном `domains`, решения — в `decisions`.
Оба списка непустые. `specs[].path` задаётся от корня OpenSpec и заканчивается
на `specs/<capability>/spec.md`. Разрешены файлы change, основной спецификации
и архива. Пути не выходят за свои корни, включая симлинки.

Список файлов задаёт всю область проверки. CLI не объединяет delta с основной
спецификацией. Если нужно проверить обе, перечислите обе. Назовите проверенные
файлы в выводе; не распространяйте их покрытие на всю wiki или весь OpenSpec.
Если в двух файлах повторяются ID, выберите нужный снимок или разделите область
проверки. Карта не скрывает дубли автоматически.

Каждый OpenSpec Scenario имеет одну запись в `links`. В ней укажите его
родительский Requirement, один или несколько wiki Requirement и Scenario.
Для каждого связанного wiki Scenario включите его родительский wiki Requirement.
Массивы разрешают связь нескольких оснований с одним сценарием.
Обратный индекс строится из этих записей; второй ручной список не нужен.

Все wiki ID из объявленных файлов должны быть покрыты или явно исключены.
Область OpenSpec должна содержать хотя бы один Scenario; пустая спецификация не проходит проверку.
Для отложенного требования или сценария добавьте:

```json
{"id": "WK-INV-S09", "reason": "Отложено решением о scope до следующей версии"}
```

Исключение имеет непустую причину, не считается покрытием и не может быть связано.
Родитель и дочерние сценарии исключаются отдельно. OpenSpec Scenario исключать
нельзя: каждый сценарий выбранной спецификации требует основания.

## Проверка

Запустите из целевого проекта:

```bash
bin/wiki/trace invites --json
bin/wiki/trace invites --require-reviewed
```

Без имени feature проверяются все карты в `domains`.
Команда только читает файлы. JSON содержит область проверки, счётчики,
прямые связи с путями и строками, обратный индекс по wiki ID и замечания.

CLI проверяет наличие файлов и ID, уникальность, родителей, полноту связей,
причины исключений и актуальность записи смысловой проверки.
Ошибки трассировки также входят в `bin/wiki/lint` при подключённом OpenSpec.
Проверка не ищет ещё не перечисленные источники и не оценивает их смысл.

Покрытие OpenSpec считается как `linked / total` для требований и сценариев.
Wiki показывает `total`, `in_scope`, `covered`, `excluded` отдельно.
При нулевом числе карт сообщайте «карты отсутствуют», без вывода о полном покрытии.
Обычный вызов возвращает `0` без структурных ошибок, даже при `pending` или `stale`.
`--require-reviewed` требует хотя бы одну карту и готовность каждой выбранной карты.
Код `1` означает незавершённую проверку, `2` — ошибку вызова или профиля.

## Смысловая проверка

Для каждого Scenario сравните Given/When/Then с wiki-сценарием, условиями,
ролями, ограничениями и решением о scope. Проверьте происхождение требований,
противоречия и отличия желаемого поведения от реализации.
Наличие ID и одинаковых слов недостаточно.

После проверки добавьте в `review`:

- `status`: `reviewed`;
- `reviewer`: кто выполнил проверку;
- `note`: что проверено и какой вывод получен;
- `fingerprint`: значение из актуального отчёта `bin/wiki/trace --json`.

Fingerprint — SHA-256 файлов из scope и определения карты без раздела `review`.
Если объявленная wiki-страница, решение, спецификация или связи изменились,
проверка становится `stale`. Источники `raw` и внешние ссылки в hash не входят.
При изменении их содержания отметьте затронутые карты как `pending` вручную
и повторите проверку оснований. CLI не обнаруживает изменение внешнего источника.
Повторите сравнение, запишите новый вывод и fingerprint.
CLI проверяет актуальность записи; достоверность вывода остаётся ответственностью проверяющего.
Не ставьте `reviewed` только ради прохождения команды.

`ready: true` означает структурную полноту и актуальную запись смысловой проверки
в объявленной области. Это не принятие решения и не готовность продукта к запуску.

## Изменения и архив

При создании спецификации зафиксируйте scope, ID и карту вместе с прямыми
и обратными Markdown-ссылками на решение. Исторические материалы не переписывайте
массово: сообщите пробелы, исправляйте только разрешённую область.

При переносе страниц сохраните ID и исправьте пути в карте. При разделении
сохраните основания каждого сценария. После архивации change явно выберите
актуальные файлы основной спецификации или архива и обновите scope.
CLI не переносит связи автоматически. Изменение требует повторной смысловой проверки.

Если спецификацию пока нельзя создать, оставьте `deferred` в решении с причиной,
ответственным и условием перехода. Не создавайте фиктивные Requirement и Scenario
для заполнения карты. Существующие разрывы остаются видимыми в отчёте.
