# Упрощенный технический русский: пишите как в руководстве по эксплуатации

Пишите технический текст по правилам УТР — упрощенного технического русского языка. УТР определен в разделе 8.2 ГОСТ Р 58049-2017. Это контролируемый язык: набор правил, которые ограничивают русский язык, чтобы читатель понял текст однозначно и с одного раза. Стандарт создан по образцу ASD-STE100 (упрощенный технический английский) для эксплуатационной документации авиационной техники.

Правила убирают признаки текста, сгенерированного нейросетью, как побочный эффект: длинные периоды, ротацию синонимов, отглагольные конструкции, вводные обороты без факта и «воду».

Пишите для усталого читателя. Каждое предложение должно быть понято с первого раза.

## Ваша задача

Когда вас просят написать или переписать технический текст:

1. **Выберите режим** (практический или строгий, см. ниже).
2. **Определите тип текста**: инструкция или описательная часть. От этого зависят остальные правила.
3. **Зафиксируйте словарь до начала работы.** Выберите ОДИН глагол для понятия «проверить» и ОДНО существительное для понятия «настройки». Других слов для этих понятий в документе нет (8.2.3.7).
4. **Примените правила** из каталога ниже.
5. **Выполните самопроверку** перед сдачей. Этот шаг обязателен.
6. **Не трогайте код**, идентификаторы, команды и цитируемые сообщения (см. «Неприкасаемое»).

Когда вас просят ПРОВЕРИТЬ текст, а не написать его, укажите для каждого нарушения: номер пункта ГОСТ, ошибочный фрагмент, исправленный вариант. Ссылайтесь только на те номера пунктов, которые есть в этом файле. Не приводите номера по памяти: модели их выдумывают.

## Два режима

| Режим | Когда | Что применяете |
|---|---|---|
| **Практический** (по умолчанию) | Документация, README, сообщения об ошибках. Пользователю нужен ясный текст | Все структурные правила. Отраслевые термины остаются («идемпотентный», «вебхук») |
| **Строгий** | Пользователь назвал УТР, ГОСТ Р 58049 или соответствие стандарту | Структурные правила плюс дисциплина терминологии. Предупредите пользователя: полное соответствие требует терминологической базы и глоссария проекта (8.1.3—8.1.8), которых в стандарте нет |

## Шаг 1: определите тип текста

| | Инструкция (8.2.5) | Описательная часть (8.2.6) |
|---|---|---|
| Назначение | Сказать читателю, что сделать | Объяснить, что это и как работает |
| Форма глагола | Повелительное наклонение, множественное число: «Установите насос» | Настоящее или прошедшее время, неопределенно-личные и безличные конструкции |
| Предел длины | **20 слов** (8.2.5.1) | **20 слов** (8.2.6.1) |
| Единица | Одна команда в предложении (8.2.5.2) | Одна тема в абзаце, максимум шесть предложений (8.2.6.2) |

Не смешивайте типы в одном фрагменте. Раздел «Быстрый старт» — инструкция. Раздел «Архитектура» — описательная часть. Примечание внутри инструкции — описательная часть: оно дает информацию, а не команду (8.2.3.19).

> **Отличие от ASD-STE100:** в английском стандарте описательный текст получает лимит 25 слов. В УТР лимит одинаковый — 20 слов для обоих типов.

## КАТАЛОГ ПРАВИЛ

Пункты приведены с номерами ГОСТ Р 58049-2017 и пересказаны своими словами с примерами из программной документации. Точные формулировки — в тексте стандарта.

### 8.2.3 Общие требования к составлению документации

| Пункт | Требование |
|---|---|
| 8.2.3.1 | Текст должен быть прост для восприятия и понимания. |
| 8.2.3.2 | Смысловые единицы текста должны пониматься однозначно. |
| 8.2.3.3 | Используйте неопределенно-личные и безличные конструкции, действительный залог, повелительное наклонение во множественном числе. |
| 8.2.3.4 | Прямой порядок слов. В простом предложении запрещено ставить подлежащее в конец и прямое дополнение перед сказуемым. |
| 8.2.3.5 | Запрещены метафоры, сравнения, сленг и жаргон. |
| 8.2.3.6 | Не применяйте иностранные слова при наличии равнозначных русских (ГОСТ 2.105, пункт 4.2). |
| 8.2.3.7 | Терминология стандартная и единообразная. Один и тот же термин для одного и того же объекта во всем тексте. Синонимы для одного понятия запрещены. |
| 8.2.3.8 | Сокращайте официальные технические термины. При выборе берите самый короткий и простой вариант. Сокращения вносите в глоссарий. |
| 8.2.3.9 | В описании порядка действий применяйте глаголы в повелительном наклонении во множественном числе. Глагол стоит на первом месте. Единственное число запрещено. |
| 8.2.3.10 | Не используйте три и более существительных подряд. Используйте глаголы вместо номинативных конструкций. Исключайте предлоги, если они не влияют на понимание. |
| 8.2.3.11 | Ограничивайте причастия, деепричастия и составные сказуемые, если это не ведет к потере смысла. |
| 8.2.3.12 | Используйте союзы для объединения предложений, описывающих последовательность действий, если выполнить 8.2.3.14 невозможно. |
| 8.2.3.13 | В инструкциях избегайте страдательного залога. |
| 8.2.3.14 | Где возможно, заменяйте сложные распространенные предложения на простые распространенные. |
| 8.2.3.15 | Запрещены опущения и сокращения слов, если это искажает смысл. |
| 8.2.3.16 | Для перечислений в сложных текстах используйте вертикальные маркированные списки. |
| 8.2.3.17 | Скобки используйте для перекрестных ссылок, буквенных и цифровых обозначений, обособления текста, выделения побочного утверждения и иерархии подпунктов. |
| 8.2.3.18 | Не используйте слова типа «кнопка», «ссылка». |
| 8.2.3.19 | Примечания дают дополнительную информацию. |

**8.2.3.4 — порядок слов.**
Было: `Осмотр конфигурации производите при остановленном сервисе.`
Стало: `Остановите сервис, затем проверьте конфигурацию.`

**8.2.3.9 — повелительное наклонение множественного числа, глагол первый.**
Инфинитив в списке шагов запрещен: читатель не понимает, что действие выполняет он.

| Было | Стало |
|---|---|
| — установить пакет; | — установите пакет; |
| — необходимо запустить миграцию; | — запустите миграцию; |
| Настрой клиент | Настройте клиент |
| Далее выполните перезапуск сервиса | Перезапустите сервис |

**8.2.3.10 — цепочки существительных и номинативные конструкции.**
Разрывайте цепочку предлогом или заменяйте ее глаголом.

| Было | Стало |
|---|---|
| значение параметра таймаута пула соединений | таймаут для пула соединений |
| Для оформления протокола осуществляют периодический контроль параметров | Периодически контролируют параметры. Затем оформляют протокол |
| выполнение процедуры удаления записей | удаляют записи |

**8.2.3.11 — причастия и деепричастия.**
Причастный оборот всегда усложняет синтаксис. Заменяйте его придаточным со словом «который» или сокращайте до одиночного причастия перед существительным.

| Было | Стало |
|---|---|
| Сотрудник, отвечающий за выпуск релиза | Сотрудник, который отвечает за выпуск релиза |
| Ошибки, выявленные в процессе работы | Выявленные ошибки |
| Запустив миграцию, проверьте журнал | Запустите миграцию. Затем проверьте журнал |

**8.2.3.13 — страдательный залог в инструкциях.**

| Было | Стало |
|---|---|
| Резервная копия должна быть создана до миграции | Создайте резервную копию. Затем запустите миграцию |
| Токен передается в заголовке | Передайте токен в заголовке |
| На основе доработанного отчета подготавливается итоговая версия | Разработчик готовит итоговую версию отчета |

**8.2.3.18 — «кнопка» и «ссылка».**
Было: `Нажмите на ссылку, чтобы узнать больше.`
Стало: `Узнайте больше [гиперссылка].`

### 8.2.5 Требования к написанию инструкций

| Пункт | Требование |
|---|---|
| 8.2.5.1 | Короткие предложения, максимум 20 слов. |
| 8.2.5.2 | Одна команда в предложении. Две команды допустимы, только если действия выполняются одновременно. |
| 8.2.5.3 | Глаголы в повелительном наклонении во множественном числе. |
| 8.2.5.4 | Инструкция содержит как можно больше конкретных описаний нужных действий. |

**Подсчет слов (примечание к 8.2.5.1):**

- текст в скобках считается новым предложением;
- числовое значение считается одним словом;
- буквенно-цифровой идентификатор считается отдельным словом;
- аббревиатура считается отдельным словом;
- названия, предупредительные надписи и цитируемый текст считаются одним словом.

> **Отличие от ASD-STE100:** в английском стандарте текст в скобках считается одним словом. В УТР он считается отдельным предложением, и это предложение тоже подчиняется лимиту 20 слов. Длинная вставка в скобках — нарушение, а не способ уложиться в лимит.

Для программной документации это значит: `sqlpipe run --config sqlpipe.yaml` в обратных кавычках — цитируемый текст, одно слово. Длинные идентификаторы не расходуют лимит предложения.

Было: `Перед настройкой клиента вам нужно будет получить ключ API в панели управления, что можно сделать в разделе «Настройки».`
Стало: `Получите ключ API в панели управления, раздел «Настройки». Затем настройте клиент этим ключом.`

### 8.2.6 Требования к написанию описательной части

| Пункт | Требование |
|---|---|
| 8.2.6.1 | Как можно более короткие предложения, максимум 20 слов. Подсчет слов — как в 8.2.5.1. |
| 8.2.6.2 | Делите текст на абзацы. Одна тема в абзаце. Максимум шесть предложений в абзаце. Абзац из одного предложения — не чаще одного раза на каждые 10 абзацев. |

В описательной части нет повелительного наклонения. Описание объясняет, инструкция предписывает.

### 8.2.7 Требования к написанию предупреждений

Предупреждение начинается с простой и понятной команды, которая однозначно отражает его смысл. При необходимости добавьте краткое пояснение о риске или опасности. Если предупреждение содержит условие, с которым нужно ознакомиться до начала работ, начните с описания этого условия.

Никогда не прячьте команду после объяснения. Правило переносится на опасные флаги CLI, необратимые миграции и опасные параметры API.

Было:

> Обратите внимание, что в некоторых случаях возможна потеря данных, если при работе с боевой базой окажется включен деструктивный флаг.

Стало:

> ВНИМАНИЕ! Не используйте флаг `--force` для боевой базы. Флаг удаляет строки, которых нет в источнике.

|---|---|
| 8.2.4.1 | Целевой текст передает смысл исходного. Добавлять смысл, которого нет в оригинале, запрещено. |
| 8.2.4.2 | Функциональный стиль перевода соответствует стилю оригинала. |
| 8.2.4.3 | Лексика и конструкции соответствуют регистру текста. |
| 8.2.4.4 | Грамматика и терминология соответствуют конвенции текста. |
| 8.2.4.5 | Учитывайте многозначность слов. Выбирайте вариант, точный в данном контексте. |
| 8.2.4.6 | Единицы измерения переводите в систему страны назначения. В скобках указывайте исходную величину: `305 м (1000 футов)`. |

### 8.1 Терминологическая база и глоссарий

| Пункт | Требование |
|---|---|
| 8.1.3 | Внедрение УТР возможно только при наличии терминологических баз. |
| 8.1.5 | В терминологическую базу входят только термины предметной области, утвержденные для проекта. |
| 8.1.7 | Для остальной лексики ведут глоссарий: варианты перевода, нормы передачи аббревиатур, имен собственных и сокращений. |
| 8.1.10 | Если терминологию задает национальный стандарт, используйте терминологию этого стандарта. |

> **Отличие от ASD-STE100:** у английского стандарта есть готовый словарь примерно из 900 разрешенных слов. У УТР такого словаря нет. Стандарт требует, чтобы проект составил собственную терминологическую базу и глоссарий. Пока их нет, работает практический режим: структурные правила плюс терминология вашего проекта, зафиксированная один раз и неизменная.

## ДИСЦИПЛИНА СЛОВОУПОТРЕБЛЕНИЯ

Механика УТР: **одно понятие — один термин, один термин — одно понятие** (8.2.3.7).

### Лестница модальности

Инструкция для человека и промпт для агента читаются одинаково: «следует» и «желательно» читатель понимает как «необязательно».

| Вы написали | УТР пишет |
|---|---|
| следует, рекомендуется (требование) | повелительное наклонение: «Установите» |
| следует, желательно (совет) | удалите или изложите фактом: «Вариант X быстрее, потому что Y» |
| необходимо выполнить, нужно запустить | «Выполните», «Запустите» |
| может быть выполнено, возможно выполнение | «выполняют» или «выполните» |
| должен быть настроен | «настройте» |

### Проход на единообразие

Сведите частые ротации к одному термину (8.2.3.7):

- проверить / убедиться / удостовериться / верифицировать / валидировать → выберите одно
- настройка / конфигурация / параметры / опции → выберите одно
- удалить / убрать / стереть / очистить → по одному на значение, дальше не меняйте
- ошибка / сбой / проблема / неисправность → «ошибка» для ошибок, «сбой» для отказов
- запустить / выполнить / вызвать / стартовать → выберите одно
- показать / отобразить / вывести / отрисовать → выберите одно
- пользователь / юзер / клиент → выберите одно

### Заимствования (8.2.3.6)

Не применяйте иностранное слово, если есть равнозначное русское: «деплой» → «развертывание», «фиксить» → «исправлять», «чекнуть» → «проверить», «дропнуть» → «удалить», «кейс» → «случай», «фича» → «функция».

Отраслевой термин без равнозначного русского остается: «вебхук», «коммит», «кеш», «эндпоинт», «токен». Внесите его в терминологическую базу один раз (8.1.5) и дальше не меняйте.

## Неприкасаемое

Это технические обозначения. Оставляйте их точно как есть, даже если они нарушают правила словоупотребления. Каждое считается одним словом (примечание к 8.2.5.1):

- блоки кода, код в строке, идентификаторы, команды CLI, флаги, пути к файлам;
- цитируемые сообщения об ошибках и строки журнала;
- названия продуктов, имена эндпоинтов API, ключи конфигурации;
- числовые значения с единицами измерения.

## Не только документация

Те же правила, другие цели. Полные разборы — в `references/use-cases.md`:

- **Сообщения об ошибках**: что произошло (прошедшее время), причина, если известна, затем исправление в повелительном наклонении. Без «Упс», без «Пожалуйста, убедитесь», без извинений.
- **Регламенты и рунбуки**: родная территория УТР. Шаги в повелительном наклонении, условие первым, предупреждение до шага.
- **Отчеты об инцидентах**: только прошедшее время. «Мы выявили проблему, которая могла повлиять на часть пользователей» → «С 14:02 до 14:31 UTC отказало 12 % запросов».
- **Описания релизов**: несовместимые изменения оформляйте как предупреждение — сначала команда, потом риск (8.2.7).
- **Инструкции для агентов (промпты, AGENTS.md)**: системный промпт — это инструкция для читателя, который не может задать вопрос. Одна команда в предложении, никаких «следует», условие перед командой.
- **Подготовка к переводу**: исходная задача УТР. Однозначная лексика и полная грамматика снимают большую часть неоднозначности при переводе (8.2.1).

## Самопроверка перед сдачей

Этот шаг обязателен. Выполните пять проверок по черновику:

1. Посчитайте слова в трех самых длинных предложениях. Больше 20 — разделите (8.2.5.1, 8.2.6.1).
2. Найдите причастия и деепричастия по буквосочетаниям: `ющ`, `ущ`, `ащ`, `ящ`, `вш`, `нн`, `-вши`, `-ясь`. Замените придаточным со словом «который» или отдельным предложением (8.2.3.11).
3. Найдите `является`, `осуществля`, `производится`, `выполняется`, `должен быть`. Замените глаголом действия или повелительным наклонением (8.2.3.10, 8.2.3.13).
4. Найдите каждое `если` и `при условии`. Каждое стоит В НАЧАЛЕ своего предложения, перед командой. «Увеличьте таймаут, если сеть медленная» → «Если сеть медленная, увеличьте таймаут» (8.2.7).
5. Найдите глаголы, которые вы НЕ выбрали на шаге 3 раздела «Ваша задача» (набор «проверить / убедиться / удостовериться»). Замените каждое вхождение выбранным словом (8.2.3.7).

Исправьте найденное, затем сдавайте. Для полной проверки пройдите `references/checklist.md`.

## Полный пример

**Было (типичный вывод нейросети):**

> **Таймауты соединения.** Если sqlpipe зависает или завершается с ошибкой `dial tcp: i/o timeout`, необходимо проверить, что хост, на котором запущен sqlpipe, имеет сетевой доступ к порту Postgres (обычно 5432) — как правило, соединение блокируется правилами файрвола или группой безопасности. При использовании управляемой базы данных (RDS, Cloud SQL и т. п.) следует убедиться, что инстанс разрешает подключения с IP-адреса sqlpipe. Также можно попробовать увеличить `source.connect_timeout_seconds` в конфигурации, поскольку медленный сетевой маршрут может приводить к срабатыванию таймаута по умолчанию.

**Стало (тип — инструкция, глагол «убедитесь», условия первыми, одна команда в предложении):**

> **Таймауты соединения.** sqlpipe останавливается с ошибкой `dial tcp: i/o timeout`, когда не может обратиться к порту Postgres (по умолчанию 5432).
>
> 1. Убедитесь, что хост с sqlpipe имеет доступ к порту Postgres. Обычно порт закрывает файрвол или группа безопасности.
> 2. Если база данных управляемая (RDS, Cloud SQL), убедитесь, что она принимает подключения с адреса sqlpipe.
> 3. Если сеть медленная, увеличьте `source.connect_timeout_seconds` в настройках.

Что изменилось: предложение на 43 слова разделено на части короче 20 слов (8.2.5.1); «проверить» и «убедиться» сведены к одному глаголу (8.2.3.7); причастные обороты «на котором запущен», «поскольку может приводить» убраны (8.2.3.11); инфинитивы и «необходимо / следует» заменены повелительным наклонением множественного числа (8.2.3.9); каждое условие перенесено в начало предложения (8.2.7); «и т. п.» удалено; код и текст ошибки не тронуты.
