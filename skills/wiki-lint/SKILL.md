# Проверка wiki проекта

Этот навык отвечает за финальную проверку всех операций изменения wiki,
включая глоссарий. Сначала выполняй механические проверки, затем смысловые.

Перед процедурой полностью прочитай [общий контракт набора](../wiki-query/references/contract.md),
затем разрешённые `knowledge/SCHEMA.md` и `knowledge/index.md`. Применяй
профиль путей, правила подключённых интеграций и контекст целевого проекта.
Отключённые документы пропускай; важные сведения сохраняй в действующих
страницах, не создавая отключённые файлы.

## Режимы

- `dry-run` — режим по умолчанию для отдельного запроса проверить wiki:
  только анализ и замечания, без записи в wiki, журнал или новые снимки источников.
- `fix` — механическая сортировка через CLI и содержательные исправления
  агентом по существующим знаниям с сохранением происхождения. Прямой запрос исправить wiki
  или завершение уже разрешённого изменения знаний разрешает этот режим.
  Не запрашивай повторное разрешение на входящие в задачу исправления.

Зафиксируй режим и границы проверки. После изменения проверяй затронутые
страницы и их связи; при отдельной проверке применяй границы запроса.
Если они не ограничены, проверяй текущие предметные страницы и представления.
Механические команды проверяют корпус по профилю целиком; это не расширяет
разрешённые границы исправлений. Несвязанные замечания сообщай отдельно.

CLI и навык имеют разные границы: `bin/wiki/lint --fix` **только сортирует**
целые записи глоссария и повторяет механическую проверку всей wiki. Он не
находит все пропущенные термины и не создаёт определения.

Выполни из корня целевого проекта:

```bash
bin/wiki/lint --dry-run
bin/wiki/status
bin/wiki/find-orphans
```

В Git checkout дополнительно выполни `git diff --check`.

Обычный CLI lint равен `--dry-run`; оба ничего не записывают. `--fix` и
`--dry-run` несовместимы. Коды завершения: 0 — нет блокирующих ошибок, 1 — они есть,
2 — ошибка вызова/инструмента. CI использует только проверку корпуса.

Блокирующие ошибки CLI: отсутствующие цели относительных ссылок, абсолютные
локальные ссылки и пути, выходящие за границы проекта, в том числе через
симлинки; неверные имена файлов решений и повтор нормализованного H1 внутри
одного домена; отсутствующий включённый глоссарий, отсутствие H2-записей,
пустой заголовок или тело записи, повтор полного нормализованного заголовка
и нарушение алфавитного порядка.
Непустое тело записи ещё не означает наличие определения: его содержание
проверяет агент. Симлинки с целью внутри проекта допустимы для чтения;
CLI отказывается записывать глоссарий через симлинк, включая родительские каталоги.
Дефолтный порядок: латиница A–Z, затем кириллица А–Я;
`ё` сортируется как `е`. Профиль может выбрать `unicode` для других языков.
При сравнении заголовков глоссария регистр, обратные кавычки и лишние пробелы
не влияют на результат. `Decision` и `Verdict` различают записи «Решение».
CLI `--fix` не удаляет дубли и не заполняет пустые записи.
Предупреждения требуют анализа и не меняют код завершения. Отсутствие входящих
ссылок или прямой ссылки из индекса — кандидат для проверки; вспомогательная
страница не обязательно требует отдельного пункта индекса.

## Сверка глоссария

При подключённом OpenSpec CLI lint также проверяет карты по
[контракту трассировки](../wiki-query/references/traceability.md).
Для выбранной функции выполни `bin/wiki/trace <feature> --json` и проверь область отчёта.
Отсутствие карт не считается покрытием. `--fix` не создаёт карты, не меняет
ID и не ставит `reviewed`. Смысловое соответствие проверяй отдельно.
Перед передачей изменённой спецификации в реализацию требуется
`bin/wiki/trace <feature> --require-reviewed` для относящихся к задаче карт.

После изменения знаний прочитай разрешённый `knowledge/GLOSSARY.md` и затронутые
статьи. Применяй [общие правила глоссария](../wiki-query/references/glossary.md).
Если `documents.glossary` равен null, проверяй термины в контексте статей,
не создавай файл и не требуй сортировки отключённого документа.
Найди новые или изменившиеся предметные понятия и технические сокращения,
которые нужны для понимания этих страниц, по заголовкам, тексту и синонимам.
Для каждого кандидата проверь существующее определение, предметный контекст,
каноническое название, английское уточнение и поле `_Avoid_`.
Проверь основания выбора названия и отказа от альтернатив; отдельного списка
допустимых синонимов быть не должно. Похожие названия не доказывают, что понятия
совпадают; конфликтующие определения и названия требуют явного замечания,
а не автоматического объединения.
Отсутствие определения нужного для понимания термина — замечание даже при
нуле ошибок CLI. Проверь также качество существующих определений в границах
проверки: наличие записи
и ссылки не означает, что она объясняет понятие.
В `dry-run` сообщи термин, место употребления и основание для определения.
В `fix` добавь или уточни краткое определение с относительной ссылкой на
каноническую страницу по общим правилам. Неоднозначное или неподдержанное
определение не придумывай: оставь явное нерешённое замечание с причиной.
Ноль ошибок CLI не подтверждает полноту терминологии или качество определений.

## Смысловая проверка

При наличии метаданных примените [общие правила](../wiki-query/references/metadata.md).
Проверьте связь утверждений с источниками, уникальность ID внутри страницы, даты и область проверок.
Проверьте сведения из YAML и ограничения поддержки сносок отдельно от отчёта CLI.
Для перепроверки фактов используйте `wiki-audit`. Исправление оформления не обновляет `verified`.
Метаданные без замечаний не подтверждают соответствие корпуса OKF.

1. Проверь, что важные канонические страницы доступны через смысловой индекс.
   Для ссылок проверь соответствие цели смыслу текста, а для ссылок с якорями —
   наличие нужного раздела. CLI не проверяет якоря, содержание целей или
   доступность внешних URL.
2. Ищи конкурирующие страницы по заголовкам, названиям из `_Avoid_`,
   употреблениям в источниках и утверждениям. Различи канонические,
   вспомогательные, исторические страницы и реальные дубли до объединения.
   Разные понятия и области применения не объединяй из-за похожих названий;
   для подтверждённых дублей используй `wiki-merge` в разрешённых границах.
3. Проследи значимые утверждения до подходящих оснований: первичных материалов,
   решений, спецификации или свидетельств реализации. Основания не обязательно
   находятся в `raw/`. Отметь отсутствующие ссылки, неясное происхождение,
   даты и несовпадение контекста. Проверка истинности и свежести внешних
   утверждений относится к `wiki-audit`; укажи необходимый аудит и не выдавай
   успешный lint за его результат.
4. Сохрани противоречия и исторические основания; не выбирай удобную версию.
5. Отметь страницы знаний, которые содержат только исходные материалы,
   список цитат или результаты эксперимента без связанных выводов.
6. Различай входящий материал, предположение, решение, спецификацию,
   реализацию и наблюдение работы системы. При исправлении оформления
   не принимай и не отменяй решения, не выдавай спецификацию за реализацию.
   В подключённой спецификации проверь затронутые прямые и обратные ссылки;
   полноценную проверку оснований и покрытия решения выполняй через `wiki-audit`.
7. Проверь новый и изменённый авторский текст по
   [каталогу технического письма](../wiki-query/references/writing.md).
   Сначала проверь сохранение смысла, затем длину, грамматику и терминологию.
   В `dry-run` сообщи нарушения и локальные исключения; в `fix` исправляй
   только разрешённые фрагменты. Успех CLI не заменяет эту самопроверку.

## Завершение изменения (обязательно в режиме fix)

1. Заверши сверку терминов и содержательные правки глоссария; проверь границу
   определения и применения и сохранность вынесенных проектных утверждений.
2. Согласуй навигацию и ссылки затронутых страниц. Обязательно проверь индекс
   и включённые метастраницы по таблице ниже; запись зависит от последствий
   исправления. Индекс не генерируется целиком из дерева файлов.
3. Выполни `bin/wiki/lint --fix`, затем обязательно `bin/wiki/lint --dry-run`
   и `bin/wiki/status`. Повтори релевантный поиск воздействия и проверку
   сирот, если менялись страницы или ссылки. Разбери оставшиеся замечания; после дополнительных
   правок повтори проверку. Не завершай задачу с необъяснёнными замечаниями.
4. Выполни дополнительные проверки харнеса проекта, `git diff --check`,
   `git diff --cached --check`
   и `git status --short`; для новых файлов также
   `git diff --no-index --check -- /dev/null <path>`.
   Тесты самого инструмента выполняются при его изменении;
   проверки корпуса не зависят от наличия тестового набора проекта. При правках
   подключённого OpenSpec выполни `openspec validate --all --strict`
   доступным CLI; отсутствие CLI сообщи как ограничение проверки спецификации.
   Проверки Git применяются только в Git checkout.

## Индекс и метастраницы после исправлений

Пути разрешаются через профиль проекта. Отключённые документы пропускай.

| Страница | Когда обновлять |
| --- | --- |
| `knowledge/index.md` | Изменились канонические страницы, их границы, ссылки или смысловая навигация |
| `knowledge/synthesis.md` | Исправление влияет на общий вывод, существенный риск или ссылки |
| `knowledge/ASSUMPTIONS.md` | Исправление влияет на формулировку предположения, его основания или ссылки |
| `knowledge/OPEN-QUESTIONS.md` | Исправление влияет на формулировку вопроса, его основания или ссылки |
| `knowledge/GLOSSARY.md` | Уточнены определение, каноническое название, `_Avoid_`, контекст или порядок записей |
| `knowledge/log.md` | Произошло значимое изменение знания или навигации; укажи дату, основание и затронутые страницы |

Простая сортировка или исправление оформления не требует записи в журнал.
Не трогай метастраницы без последствий для их содержания или ссылок.
Схема меняется только при разрешённом изменении устройства wiki.

## Отчёт

Укажи режим, границы проверки, выполненные команды и смысловые проверки.
Для каждого замечания укажи файл и строку, категорию, основания, последствия
и минимальное обоснованное исправление. Различай блокирующие ошибки CLI,
предупреждения и смысловые проблемы, которые CLI не проверяет.

Отдельно перечисли выполненные исправления, результаты повторных проверок,
оставшиеся проблемы с причинами и непроверенные части. Ноль ошибок CLI при
нерешённых смысловых замечаниях не означает готовность корпуса. Если проблем
не найдено, это результат описанной проверки, а не подтверждение глобальной
истинности или полноты wiki. Критерии завершения и публикации всей задачи
задаёт харнес проекта.
