# Проверка wiki проекта

Этот skill владеет финальной проверкой всех операций изменения wiki, включая
глоссарий. Сначала запускай deterministic gates, затем semantic review.

Перед процедурой полностью прочитай [общий контракт набора](../wiki-query/references/contract.md),
затем разрешённые `knowledge/SCHEMA.md` и `knowledge/index.md`. Применяй
профиль путей, правила подключённых интеграций и контекст целевого проекта.

## Режимы

- `dry-run` — только анализ и findings, без записи в wiki или журнал.
- `fix` — механическая сортировка через CLI и содержательные исправления
  агентом по существующим знаниям с provenance. Прямой запрос исправить wiki
  или завершение уже разрешённого изменения знаний разрешает этот режим.
  Не запрашивай повторное разрешение на входящие в задачу исправления.

CLI и skill имеют разные границы: `bin/wiki/lint --fix` **только сортирует**
целые записи глоссария и повторяет механическую проверку всей wiki. Он не
находит все пропущенные термины и не создаёт определения.

Выполни из repository root:

```bash
bin/wiki/lint --dry-run
bin/wiki/status
bin/wiki/find-orphans
```

В Git checkout дополнительно выполни `git diff --check`.

Обычный CLI lint равен `--dry-run`; оба ничего не записывают. `--fix` и
`--dry-run` несовместимы. Exit codes: 0 — нет blocking errors, 1 — они есть,
2 — ошибка вызова/инструмента. CI использует только проверку корпуса.

Blocking errors: broken relative targets, absolute/escaping local paths и
symlinks, invalid decision filenames, duplicate normalized H1 в одном domain;
отсутствующий включённый профилем глоссарий, отсутствие H2-записей, пустое название/определение,
повтор полного нормализованного заголовка и нарушение алфавитного порядка.
Дефолтный порядок: латиница A–Z, затем кириллица А–Я;
`ё` сортируется как `е`. Профиль может выбрать `unicode` для других языков.
Регистр/backticks/лишние пробелы не влияют на сравнение. `Decision` и `Verdict`
различают записи «Решение». Fix не удаляет дубли и не заполняет пустые записи.
Advisory warnings требуют анализа и не меняют exit code.

## Сверка глоссария

После изменения знаний прочитай разрешённый `knowledge/GLOSSARY.md` и затронутые
статьи. Применяй [общие правила глоссария](../wiki-query/references/glossary.md).
Если `documents.glossary` равен null, проверяй термины в контексте статей,
не создавай файл и не требуй сортировки отключённого документа.
При отдельной проверке scope — текущие canonical domains и ролевые views.
Найди новые или изменившиеся предметные понятия и технические сокращения,
которые нужны для понимания этих страниц, по заголовкам, тексту и синонимам.
Для каждого кандидата проверь существующее определение, предметный контекст,
каноническое название, английское уточнение, синонимы и поле «Избегать».
Проверь основания эквивалентности названий и причины исключения неоднозначных
слов. Похожие названия не доказывают, что понятия совпадают; конфликтующие
определения и синонимы требуют явного finding, а не автоматического merge.
Пропущенный термин при наличии его в статье — finding даже при нуле ошибок CLI.
Проверь также качество уже существующих определений в scope: наличие записи
и ссылки не означает, что она объясняет понятие.
В `dry-run` сообщи термин, место употребления и основание для определения.
В `fix` добавь или уточни краткое определение с относительной ссылкой на
каноническую страницу по общим правилам. Неоднозначное или неподдержанное
определение не придумывай: оставь явное unresolved finding с причиной.
Ноль ошибок CLI не подтверждает полноту терминологии или качество определений.

## Semantic review

1. Проверь, что важные canonical pages доступны через semantic index; supporting
   page не обязана иметь отдельную index entry.
2. Ищи competing concepts по titles, synonyms и claims; классифицируй их до
   merge как canonical, supporting, historical или duplicate.
3. Проследи material claims до `raw/` и проверь support, scope и freshness.
4. Сохрани contradictions и stale history; не выбирай удобную версию.
5. Отметь knowledge pages, которые являются source dump, quote list или
   experiment output вместо synthesis.
6. Не смешивай inbox, assumption, decision, OpenSpec, implementation и runtime
   как один уровень истины.

7. Проверь новый и изменённый авторский текст по
   [каталогу технического письма](../wiki-query/references/writing.md).
   Сначала проверь сохранение смысла, затем длину, грамматику и терминологию.
   В `dry-run` сообщи нарушения и локальные исключения; в `fix` исправляй
   только разрешённые фрагменты. Успех CLI не заменяет эту самопроверку.

## Завершение изменения (обязательно в режиме fix)

1. Заверши сверку терминов и содержательные правки глоссария; проверь границу
   определения и применения и сохранность вынесенных проектных утверждений.
2. Согласуй навигацию и ссылки только затронутых страниц; запиши смысловой
   результат в `knowledge/log.md`. Semantic index не генерируется целиком.
3. Выполни `bin/wiki/lint --fix`, затем обязательно `bin/wiki/lint --dry-run`
   и `bin/wiki/status`. Разбери оставшиеся findings; после дополнительных
   правок повтори проверку. Не завершай задачу с необъяснёнными замечаниями.
4. Выполни дополнительные проверки харнеса проекта, `git diff --check`,
   `git diff --cached --check`
   и `git status --short`; для новых файлов также diff check относительно
   `/dev/null`. Tests самого инструмента выполняются при его изменении;
   corpus checks не зависят от наличия тестового набора проекта. При правках
   подключённого OpenSpec выполни `openspec validate --all --strict`
   доступным CLI; отсутствие CLI сообщи как ограничение проверки specs.
   Git checks применяются только в Git checkout.

## Отчёт

Успешная проверка подтверждает готовность корпуса в проверенном scope.
Критерии завершения и публикации всей задачи задаёт харнес проекта.

Для каждого finding укажи file/line, category, evidence, impact и минимальное
безопасное исправление. Отдели blocking errors от human-review warnings. Если
проблем не найдено, перечисли выполненные проверки, не заявляя глобальную
истинность или полноту wiki.
