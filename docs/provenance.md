Адаптация делает числовые и структурные правила обязательными для русского
авторского текста, сохраняя приоритет смысла, условий и степени уверенности.

## Метаданные из OKF — 2026-10-09

Источник подхода — [GoogleCloudPlatform/open-knowledge-format](https://github.com/GoogleCloudPlatform/open-knowledge-format).
Спецификация [OKF v0.2](https://github.com/GoogleCloudPlatform/open-knowledge-format/blob/ad30107c31c06aec8a7d5636e0d1058118604e6f/SPEC.md)
проверена 2026-10-09 на commit `ad30107c31c06aec8a7d5636e0d1058118604e6f`.
Каталог `knowledge-catalog/okf` заморожен; канонический источник находится в отдельном репозитории.
Это заимствование идей, без переноса кода, агента, примеров предметных данных или полного текста спецификации.

Заимствованы понятия `sources` со стабильными ID, `generated`, `verified`,
`stale_after`, а также краткие описания и типы документов.
Общие правила находятся в `skills/wiki-query/references/metadata.md`;
восемь навыков применяют их по последствиям своей операции.
Метаданные необязательны и следуют схеме целевого проекта.

Локальная адаптация сохраняет датированные снимки в raw, основания отдельных утверждений и противоречия.
Она различает содержательную правку, проверку факта, принятие решения, реализацию и наблюдение в runtime.
Прежняя проверка не подтверждает новую версию после изменения утверждения или основания.
Истечение срока означает необходимость перепроверки, а не ложность утверждения.
Состояние документа OKF не заменяет статусы решений целевого проекта.

OKF связывает утверждения со сносками по ID источников.
Текущий CLI набора не разбирает YAML и может ошибочно принять текст сноски за файловую ссылку.
Адаптация использует обычные Markdown-ссылки при добавлении отсылок и сохраняет существующие сноски до разрешённой правки формата.
Связи в метаданных, их пути и область проверок проверяет агент.
Соглашение о путях от корня bundle и мягкое отношение OKF к отсутствующим целям не перенесены в CLI.

Индексы по каталогам и граф ссылок рассматриваются как дополнение к смысловому индексу,
но их генератор не добавлен. Экспорт, импорт с преобразованием путей,
`Attested Computation` и протокол выполнения расчётов остаются вне этой адаптации.
Профиль, начальный корпус, зависимости и CLI-проверки не изменены.
Установщик включает новый общий справочник и отклоняет неполный комплект до записи.
Совместимость корпуса с OKF и выполнение расчётов эта работа не подтверждает.

## Корневые единицы raw и линтер OKF — 2026-10-09

По запросу пользователя дефолтные категории сведены к sources/research.
Для новых единиц введён корневой README.md в UTF-8 Markdown с YAML frontmatter.
Основа формы концепта — та же [закреплённая спецификация OKF v0.2](https://github.com/GoogleCloudPlatform/open-knowledge-format/blob/ad30107c31c06aec8a7d5636e0d1058118604e6f/SPEC.md),
разделы 4, 5, 7 и 11. Это заменяет прежнюю необязательность metadata только для новых root README.md.
Прежние страницы и исходные вложения сохраняются без массовой миграции.

Таксономия sources/research, дерево topic/date-slug/README.md, типы Source material/Research study,
обязательные title/description/sources, ID оснований и строгие локальные адреса —
соглашения этого набора. Они не приписываются OKF.
В OKF только type обязателен для концепта; optional families не требуются,
неизвестные types/keys и недоступные cross-links допускаются.

`bin/wiki/raw-lint` разделяет форму концепта OKF и локальный raw-контракт.
`--okf-only` не применяет дополнительные raw-требования; optional producer guidance даёт warnings.
Полное соответствие bundle, его index/log и Markdown-вложений не проверяется.
Структурная проверка не подтверждает истинность, свежесть, runtime или выполнение вычислений.
Команда не открывает внешние URL, не исполняет resources и не изменяет файлы.

Для настоящего YAML-парсинга используется [PyYAML 6.0.3](https://pypi.org/project/PyYAML/6.0.3/)
через SafeLoader с отказом от повторных mapping keys. Зависимость закреплена
в bin/wiki/requirements.txt и устанавливается пользователем явно.
Код библиотеки не копируется в набор; прочие CLI сохраняют стандартную библиотеку.
Источники изменений — issue [#18](https://github.com/mesilov/pdlc-llm-wiki4sdlc-skill/issues/18)
и [#20](https://github.com/mesilov/pdlc-llm-wiki4sdlc-skill/issues/20).

## Самодиагностика OpenSpec — 2026-10-09

`bin/wiki/doctor` использует общий валидатор путей wiki и проверяет
OpenSpec CLI и файлы skills без установки или исправлений.
Пути Codex/Claude Code/OpenCode сверены с OpenSpec CLI 1.14.1 и
[OpenSpec Supported Tools](https://github.com/Fission-AI/OpenSpec/blob/main/docs/supported-tools.md);
shared и пользовательские каталоги OpenCode — с
[OpenCode Agent Skills](https://opencode.ai/docs/skills/).
Новый путь Codex `.agents/skills` и legacy `.codex/skills` проверяются отдельно.

Не заимствованы генератор skills, YAML-парсер, workflow profiles и
настройки разрешений агентов. Минимальная проверка заголовков SKILL.md
подтверждает читаемость файла и наличие name/description, но не заменяет
проверку YAML, загрузки/разрешений агента, полноты профиля или смысла навыка.
Разные workflows и delivery settings не сводятся к фиксированному числу файлов.

## Самодиагностика forge — 2026-10-09

Реализация issue #12 расширяет doctor локальной проверкой Git remote и
клиента, а также явными сетевыми проверками. Синтаксис API и поля ответов
сверены с первичными источниками:

- [gh api](https://cli.github.com/manual/gh_api): явные `--hostname` и
  `--method GET`; команда не полагается на подстановку текущего repository.
  Реальный `gh 2.88.1` отклоняет `--hostname ghe.example:8443` до запроса
  (`invalid hostname`); doctor отдельно отклоняет нестандартный HTTPS-порт
  GitHub, сохраняя нормализацию 443 и корпоративные хосты без порта.
- [glab api](https://docs.gitlab.com/cli/api/): выбор хоста, GET и percent-encoded
  GitLab project path; чтение одной страницы с `per_page=1` достаточно для
  проверки доступа, это не сбор полного списка.
- [GitLab CLI configuration](https://docs.gitlab.com/cli/configuration/):
  ambient `API_PROTOCOL`/`GITLAB_SUBFOLDER` могут менять адрес запроса; doctor
  исключает эти переопределения, сохраняя настройки выбранного хоста, и
  отключает `GLAB_ENABLE_CI_AUTOLOGIN`, чтобы не запускать login в CI.
- [GitHub repositories API](https://docs.github.com/en/rest/repos/repos#get-a-repository):
  identity, `has_issues` и `permissions`.
- Вывод версии `gh` из пакетов [Debian](https://github.com/cli/cli/issues/12640)
  и [Ubuntu](https://github.com/cli/cli/issues/13124) может содержать пробелы
  в build annotation. Doctor принимает этот формат, но публикует только
  числовую версию, без содержимого annotation.
- [GitLab projects API](https://docs.gitlab.com/api/projects/):
  `path_with_namespace`, `web_url`, включение функций и access levels.

Из документов выведено использование раздельных GET проверок авторизации,
репозитория и списков issue/PR/MR. Заявленные API права не являются доказательством
выполненной записи. Проверки CLI/API через fixtures не доказывают работу реального
GitLab хоста; реальный read-only запуск проверен с GitHub и `gh 2.88.1`.
Исходные внешние ссылки хранятся здесь, а устанавливаемый профиль содержит
самодостаточные инструкции и локальные ссылки комплекта.
