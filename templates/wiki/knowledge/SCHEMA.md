# Схема знаний проекта

`wiki.config.json` определяет пути и соглашения. Отсутствующее поле использует
дефолт набора. Имя и язык проекта задаются профилем; scope и правила поставки —
инструкциями пользователя и AGENTS.md целевого проекта.

| Слой | Назначение |
| --- | --- |
| raw | Первичные материалы с provenance, датой, версией и контекстом |
| domains | Канонический синтез по понятиям и предметным областям |
| views | Представления по тематическим вопросам PDLC и SDLC |
| decisions | Осознанный выбор со статусом, владельцем и evidence |
| inbox | Идеи, которые пока не являются фактами или решениями |
| archive | Исторические страницы с указанием замены |

Дефолтные категории raw — `sources` и `research`.
Источники, наблюдения и проверки хранятся в sources; материалы отдельных исследований — в research.
Дерево: `<raw_root>/<category>/<topic>/YYYY-MM-DD-<slug>/README.md`.
Корневой файл новой единицы обязателен: UTF-8 Markdown с YAML frontmatter по форме OKF v0.2.
Минимум — `type`, `title`, `description`, `sources`; происхождение, даты, контекст,
состав файлов и ограничения описываются в тексте.
Оригиналы сохраняются отдельно без преобразования.
Подробности — в [описании raw](../raw/README.md) и references/raw.md установленного wiki-query.
Явный `raw_categories`, включая `[]`, заменяет defaults; пользовательские категории описываются здесь.
Прежняя структура не мигрирует автоматически. Явная схема проекта может заменить формат новых единиц.
`bin/wiki/raw-lint` проверяет дефолтное дерево и корневые файлы; `--okf-only` применяет только форму OKF.
Смысл материала, полноту оснований и соответствие собственной схеме проверяйте отдельно.

Каталоги domains/views/decisions/inbox/archive появляются по содержимому.
Профиль переопределяет пути через `knowledge_root` и `layers`.
Представления по умолчанию лежат в `knowledge/views/<lens>/`.
Явный `views` заменяет список линз; эта схема и индекс задают их цели и расположение.

| Линза | Цель |
| --- | --- |
| `product` | Ценность, границы, требования и приоритеты продукта |
| `discovery` | Пользователи, проблема, рынок, альтернативы, идеи и гипотезы |
| `experience` | Пользовательские сценарии, UX, прототипы и доступность |
| `engineering` | Архитектура, контракты, спецификация, код и тесты |
| `go-to-market` | Позиционирование, цена, каналы и запуск |
| `operations` | Эксплуатация, поддержка, надёжность, инциденты и стоимость |
| `measurement` | Критерии успеха, метрики, эксперименты и результаты проверок |

PDLC содержит шесть этапов: Discovery, Definition, Design, Development, Launch, Optimization.
Discovery включает Ideation; Validation проходит через все этапы.
Линзы охватывают вопросы PDLC и SDLC, но не задают статусы или обязательный последовательный процесс.

Выбирайте основную линзу по цели материала.
Добавляйте другие линзы только при влиянии на их содержание.
Сохраняйте канонические факты в domains, а решения — в decisions.
Связывайте представления с каноническими страницами без копирования источников.
Создавайте страницы только при наличии самостоятельного содержания.
Сохраняйте прежние папки до явного запроса на изменение структуры.

`views: []` отключает дефолтную карту без удаления страниц; автоматической миграции нет.

Глоссарий содержит H2-записи с каноническим названием, кратким определением
и переходом к контексту по относительному адресу. Запись может содержать `_Avoid_`:
нежелательные альтернативные названия и синонимы с причиной. Отдельного списка
допустимых синонимов нет. В новых объяснениях используется каноническое название;
варианты из `_Avoid_` помогают искать старые употребления. Синонимы одного
понятия не требуют отдельных записей; одинаковое слово для разных понятий
не делает их синонимами.

Условия применения, лимиты и реализация остаются на профильных страницах.
Статусы решения по умолчанию: proposed, accepted, rejected,
superseded. Имя файла по умолчанию: YYYY-MM-lowercase-kebab-case.md.

Факт, предположение, решение, спецификация, реализация и проверка в runtime —
разные уровни подтверждения.
OpenSpec подключается только явным openspec_root; обычное обновление знаний
не создаёт спецификацию и не подтверждает реализацию.

Сохраняйте противоречия и неизвестные явно.

При подключении OpenSpec карты `traceability.json` под domains связывают wiki с требованиями и отдельными сценариями.
Каждая карта явно задаёт `wiki_files`, `specs` с `{capability, path}`, `decisions` и `links`.
Requirement и Scenario имеют стабильные `[ID]`; названия могут меняться без смены ID.
`bin/wiki/trace` проверяет структуру карты, а `--require-reviewed` требует ручной статус `reviewed` и актуальный fingerprint.
Смысловое соответствие, права решения, реализацию и runtime проверяют отдельно.

После archive вручную выберите актуальные specs.
Повторите проверку карты.
