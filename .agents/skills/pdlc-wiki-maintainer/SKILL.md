# Мейнтейнер PDLC LLM Wiki Skills

Веди изменения этого репозитория по цепочке
`запрос → issue → рабочая ветка → PR в dev → ревью → dev → релизный PR в main`.
На GitHub запрос на слияние называется Pull Request (PR); пользовательское
«MR» означает тот же объект.

Это локальный навык обслуживания набора. Не копируй его в `skills/wiki-*`,
шаблоны или defaults целевых проектов. Он не разрешает сам по себе merge,
публикацию релиза или изменение настроек GitHub: выполняй их в рамках
поручения пользователя. Подготовка PR не означает поручение выпустить релиз.

## Контекст проекта

Сначала прочитай [AGENTS.md](../../../AGENTS.md), проверь cwd, Git status,
remote и актуальные ветки. Сохраняй чужие tracked, untracked и ignored файлы;
в коммит включай только свой scope. Для изоляции используй отдельный worktree,
если текущий checkout содержит несвязанные изменения.

- `skills/wiki-*/SKILL.md` — восемь устанавливаемых wiki-навыков.
- `skills/wiki-query/references/` — общий контракт и настраиваемый профиль.
- `bin/wiki/` — CLI; `scripts/install.py` — установка; `templates/wiki/` —
  нейтральные данные начального корпуса, а не правила для текущей работы.
- Изменение профиля требует согласовать CLI, контракт, `profile.md` и тесты.
  OpenSpec подключается явно; обязательные внешние сервисы не добавляй.
- Сохраняй provenance и видимость противоречий. Различай факт, гипотезу,
  решение, спецификацию, реализацию и подтверждённое выполнение.

## Ветки и планирование

| Объект | Правило |
| --- | --- |
| `main` | Защищённая ветка выпущенного состояния; без прямого push, force push и обхода protection |
| `dev` | Накопление изменений следующего релиза |
| Рабочая ветка | От актуальной `origin/dev`; обычно `codex/<тема>` |
| PR изменения | Целевая ветка строго `dev` |
| Релизный PR | Продвижение `dev → main` через обычное ревью |
| GitHub milestone | Версия релиза, его scope и критерии готовности |

Это требуемая политика, а не доказательство настройки branch protection.
Перед merge проверь фактические правила GitHub. Если `dev` не найдена,
перепроверь remote; не подменяй её `main`. Сообщи о необходимости настройки
ветки, не создавай её и не меняй protection без соответствующего поручения.

## Запрос на изменение

1. Найди issue, соответствующее запросу, или создай его до реализации.
   Зафиксируй проблему, scope и проверяемый результат. Доработка того же
   запроса использует его issue; отдельный новый scope получает отдельное issue.
   Это относится и к документации, навыкам, шаблонам и другим малым изменениям.
2. Назначь issue и PR в milestone планируемого релиза. Используй существующий
   milestone нужной версии; новый создавай при планировании нового релиза.
   Если версия ещё не выбрана, явно отметь неназначенный milestone и уточни
   план релиза, не придумывай версию или срок.
3. Обнови сведения об `origin/dev`, создай рабочую ветку и выполни изменение.
   В [CHANGELOG.md](../../../CHANGELOG.md) добавь содержательную запись
   в `Unreleased`: что изменилось для пользователя набора. Укажи issue;
   breaking changes и миграцию назови явно. Не заполняй историю догадками.
   При подготовке релиза перенеси накопленные записи в датированный раздел
   версии; отдельная запись «подготовлен релиз» не нужна.
4. Проверь результат командами ниже. Создай PR в `dev`, свяжи его с issue
   (`Closes #N`, когда PR полностью выполняет запрос), укажи milestone,
   назначение изменения, проверки и существенные ограничения.
5. Пройди ревью и повтори проверки на актуальном состоянии PR. Merge выполняй
   только после снятия всех замечаний и проверки changelog внутри этого PR.

## Проверки изменения

Из корня репозитория запускай:

```bash
python3 -m unittest discover -s tests -t .
git diff --check
```

Новые untracked файлы проверь отдельно на trailing whitespace и корректный
конец файла: обычный `git diff --check` их не видит. Перед коммитом проверь
состав staged файлов и `git diff --cached --check`.

Новый или изменённый навык проверь валидатором навыков, если он доступен,
и сценариями принятия решений. Структурная проверка не доказывает качество
инструкций. Установку проверяй только в отдельном временном проекте:

```bash
python3 scripts/install.py /path/to/temporary-project --init-wiki --dry-run
python3 scripts/install.py /path/to/temporary-project --init-wiki
```

Для изменения устанавливаемых ресурсов проверь их наличие и работу CLI
в целевом проекте. Для локального навыка проверь, что он туда не копируется.
Не устанавливай набор в собственный checkout.

## Все замечания до merge

Прочитай описание PR, общие комментарии, reviews и все review threads,
включая outdated. При чтении API обработай все страницы. Один вывод
`gh pr view --comments`, approval или зелёный CI не подтверждают снятие
всех замечаний; состояние review threads проверяй через GitHub UI или API.

Для каждого замечания зафиксируй действие и результат: исправление с commit
и проверкой либо согласованное с reviewer объяснение, почему правка не нужна.
Ответь в исходном обсуждении. Закрывай тред после проверки результата;
не используй `resolved` как замену исправлению или согласованию.
Обычные комментарии с замечаниями тоже требуют ответа и снятия вопроса,
хотя у них нет флага `resolved`. Информационные сообщения не требуют правок.

Перед merge одновременно должны выполняться условия:

- Все замечания обработаны; нет открытых review threads, unanswered замечаний
  и неснятого `Changes requested`. Выполнены обязательные approvals GitHub.
- Required checks прошли для текущего head PR. После новых коммитов
  перепроверь reviews, комментарии, треды и checks.
- В diff PR относительно актуальной целевой ветки есть содержательная запись
  `CHANGELOG.md` именно об этом изменении; она сохранена в текущем head.
  Проверь diff и текст файла, а не только наличие пути в списке файлов.
  Уже существующая запись в `dev`, обещание добавить её позже, удаление
  записи или правка только пробелов это условие не выполняют.
  При подготовке релиза перенос накопленных записей в датированный раздел
  версии считается содержательным изменением changelog.
- PR по-прежнему направлен в нужную ветку, связан с issue и не содержит
  посторонних изменений. Нет конфликтов или обхода branch protection.

Если обсуждения или checks недоступны, готовность к merge не подтверждена.
Отсутствие записи changelog блокирует merge, даже для документации.
Если правильная запись уже попала в `dev`, не создавай дубль или фиктивную
правку ради diff. Добавь необходимое содержательное уточнение о фактическом
изменении, если оно есть. Иначе сообщи о конфликте с правилом и оставь merge
заблокированным до решения пользователя; самостоятельно исключение не вводи.

Пример: PR в `dev` имеет approval и зелёный CI, но запись changelog попала
напрямую в `dev`, а старое замечание осталось открытым. Обработай оба
блокирующих условия по правилам выше и повтори весь контроль для нового head.
До этого merge заблокирован.

## Релиз через GitHub milestone

1. Проверь scope milestone: входящие issue и PR, оставшиеся задачи,
   changelog и подтверждённые merges в `dev`. Открытые задачи не считаются
   выполненными; перенос в другой milestone требует явного решения о scope.
2. Подготовь версию и датированный раздел `CHANGELOG.md` из `Unreleased`
   отдельным изменением через issue и PR в `dev`. Сохрани записи, ссылки,
   breaking changes и инструкции миграции; не включай незавершённые задачи.
3. Открой релизный PR `dev → main`, связанный с milestone и issue подготовки
   релиза. Это единственное исключение из цели `dev` для PR. Примени те же
   проверки замечаний, changelog внутри diff и обязательных checks.
4. При поручении выпустить релиз выполни merge, проверь попадание результата
   в `main`, создай tag и GitHub Release для подтверждённого commit в `main`.
   Название milestone, версия changelog, tag и release должны обозначать
   одну версию; следуй существующему формату тегов.
5. Закрой milestone после подтверждённой публикации и завершения его scope.
   Сообщи ссылки на issue, PR, milestone и release, merge commit и результат
   проверок. Если публикация не выполнена, назови фактически достигнутый этап.

Merge в `dev`, локальные тесты, наличие tag и опубликованный GitHub Release
подтверждают разные этапы. Не объявляй релиз опубликованным по одному из
промежуточных результатов.
